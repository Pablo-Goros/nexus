## Stage III Assignment (summary of the enunciado)

The final stage completes the compiler with two new phases plus documentation.

### Phase 1 — Semantic Analysis (Análisis Semántico, v0.2.0)
Operate on the AST to validate the program against the domain. The supporting docs describe the
standard toolkit, which the implementation should apply to the graph domain:

- **Tabla de Símbolos** — a database of declared constructs (create / update / read operations),
  usually a hash-map/dictionary keyed by identifier. Holds graphs, nodes, groups, analyses, results, etc.
- **Scopes** — a stack of symbol tables; push on block entry, pop on exit. Lookup walks the stack
  from the top. Nexus has nested scopes (graph body, per-graph node/group namespaces, analysis body,
  `forall` binding the loop variable).
- **Sistema de Tipos** — `type(node)` synthesized bottom-up over the AST; returns the node's domain
  "type" or `⊥` (bottom) when malformed. Includes type-checking and (optionally) coercion/inference.

For Nexus the "type system" is reinterpreted as **graph-property checking**. Validations to implement
(these are exactly the Stage II non-goals deferred to Stage III, see `plan.md`):

- Duplicate identifiers: graph, node, group, analysis, result.
- Undeclared references: node, group, graph, result.
- `weight` / `capacity` only allowed when the matching trait (`weighted` / `capacitated`) is declared.
- Edge operator vs. graph kind: `->` requires `directed`, `--` requires `undirected`.
- Constraint vs. graph kind (e.g. `strongly_connected` only for directed).
- Transformation vs. source graph kind (e.g. `transpose` only meaningful for directed).
- Algorithm vs. graph kind and traits (e.g. `mst` needs weighted; `max_flow` needs capacitated
  + directed; `topological_sort` needs directed; `shortest_path` needs weighted, etc.).

### Phase 2 — Code Generation (Generación de Código, v0.1.0) + Runtime (v0.1.0)
Translate the validated AST into the final artifacts by walking the tree with a `generate(node)`
function that emits output via an `output(...)` sink. The designer decides what is generated by the
compiler vs. what belongs to the **runtime** (delegated to the client's environment). The enunciado
stresses the domain determines *"la relevancia o no del Runtime"* — i.e. whether a runtime is needed
at all is a design choice for this language.

## The Nexus Language

A program is one or more top-level declarations: **graph**, **derive**, **analysis**.

```nexus
graph G:
    kind directed                 # required: directed | undirected
    traits weighted capacitated   # optional traits
    nodes:
        a source                  # optional node attr: root | source | sink | terminal
        b
        c sink
    edges:
        a -> b weight 2           # -> directed, -- undirected; optional weight/capacity
        b -> c capacity 5
    groups:
        core = {a, b}
    constraints:
        assert reachable a -> c    # connected | strongly_connected | acyclic |
                                   # reachable u -> v | tree rooted_at r |
                                   # binary_tree rooted_at r |
                                   # forall n in group: <degree-predicate>

derive R from G using transpose    # transpose | induced_subgraph(group) |
                                   # remove_self_loops | underlying

analysis Main on G:
    run shortest_path from a to c as path   # shortest_path | topological_sort |
                                            # components | scc | mst | max_flow
    export graph to dot                      # dot | json
    export result path to json
```

Degree predicates: `indegree(n)`, `outdegree(n)`, `degree(n)` compared with `= != >= <= < >`.

## Codebase Map

Built from `https://github.com/agustin-golmar/Flex-Bison-Compiler/tree/v2.0.0`. C, CMake, Docker.

- `src/main/c/EntryPoint.c` — pipeline: parse → `executeCalculator` (stub) → `executeGenerator` (stub).
- `src/main/c/frontend/lexical-analysis/FlexPatterns.l` — Nexus lexer.
- `src/main/c/frontend/syntactic-analysis/BisonGrammar.y` — Nexus grammar + semantic actions.
- `src/main/c/frontend/syntactic-analysis/AbstractSyntaxTree.{h,c}` — full AST types,
  constructors, destructors. **This is the input contract for Stage III.**
- `src/main/c/backend/domain-specific/Calculator.{h,c}` — STUB (leftover calculator). Candidate to
  become / be replaced by the **semantic analyzer**.
- `src/main/c/backend/code-generation/Generator.{h,c}` — STUB. Candidate to become the **code generator**.
- `src/main/c/support/type/CompilerState.h` — holds `abstractSyntaxtTree` + a leftover `value` field;
  has TODOs to add a symbol table and a scope stack.
- `src/main/c/support/` — logging, string, environment, types (reusable infra).
- `src/test/c/accept/` (31 programs) and `src/test/c/reject/` (12 programs) — Stage II tests.

### AST entry contract (see `AbstractSyntaxTree.h`)
Root: `Program { TopLevelDeclList * decls }`. Each `TopLevelDecl` is a tagged union over
`GraphDecl` / `DeriveDecl` / `AnalysisDecl`. Graphs carry `GraphKind`, `GraphTraits {weighted,
capacitated}`, and linked lists of `NodeDecl`, `EdgeDecl`, `GroupDecl`, `Constraint`. Analyses carry
`AnalysisStmt` (run/export). All enums for kinds, attrs, operators, constraint/algorithm/transform
types, comparators, and formats already exist.

## Build / Run / Test

```bash
docker compose run --rm compiler      # ephemeral dev container
src/main/bash/build.sh                 # build
src/main/bash/test.sh                  # run accept/reject suites
src/main/bash/run.sh <program>         # compile one program
```

Acceptance: builds clean in Docker, no Bison conflicts, accept tests exit 0, reject tests exit non-zero,
parsed program stores a non-null AST root in `CompilerState`.
